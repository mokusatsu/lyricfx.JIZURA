# 各実装段階のGitHub Pages公開と人間確認

2026-10-18の利用者指定により、AVOID-002〜018の各段階は、GitHub Pagesへ出力した版を人間が確認する。担当エージェントは公開と反映確認を済ませてから、操作可能なURLと確認ポイントのリストをこの会話で提示する。口頭の説明やローカル試験の成功だけで人間確認を代替しない。

これは後続実装の受入手順を定める文書であり、この計画スレッドで実装を開始する指示ではない。公開依頼と、人間による実装結果の判定は区別する。各段階で公開許可を聞き直す手順は設けず、依頼された実装・公開・事前検証を済ませてから結果の確認を依頼する。

## 公開先と確認した根拠

- リポジトリ: `mokusatsu/lyricfx.JIZURA`。公開元ブランチは利用者が設定した `work`（2026-10-18の会話による確認）。公開元を勝手に`main`へ変更しない。
- アプリURL: `https://mokusatsu.github.io/lyricfx.JIZURA/`、英語版: `https://mokusatsu.github.io/lyricfx.JIZURA/en/`。既存の `mcp/site-smoke-test.mjs` もこの日本語URLを既定値とする。
- README.mdの冒頭には別フォークのURLが残っている。各段階の確認依頼にそのURLを流用しない。
- `.github/workflows/verify.yml` は検証用で、Pagesをデプロイする処理はない。Pagesの自動公開と検証CIを別々に確認する。`work`へのpushだけではこのverify workflowの自動実行を意味しない（現行はmain/pull_request/手動起動）。
- Pages設定APIの読み取りはこの環境では`Forbidden`。APIで公開元を確認できたとは記録しない。利用者の設定報告を採用し、実装段階では実際の公開HTML・確認用ファイルの反映を検証する。今回、新たな公開基盤タスクや公開設定変更は追加しない。

## 1段階の実行順

1. **実装とローカル検証**: 個別タスクの条件を満たし、関連する自動試験を実行する。基盤段階も対象とする。
2. **人間が操作できる準備**: その段階の確認用サンプル、操作入口、期待結果を用意する。AVOID-002で公開確認ページの最小構成を作り、以後は各タスクで必要なケースを追加する。未実装機能を前提に人間へ操作を指示しない。
3. **公開物を生成**: 日英HTMLを生成し、確認ページ・fixture・版を識別するmanifestを揃える。アプリ本体、公開用サンプル、manifestを同じ検証対象として扱う。公開する素材はこの試験用に作成・提供可能なものを使い、実際の演者素材は人間がブラウザ内で読み込む。
4. **コミット・プッシュ**: 当該タスクIDを付けて`work`へコミットし、`origin/work`へ通常pushする。プッシュ先の履歴に別変更があれば内容を確認して取り込み、force pushで消さない。
5. **Pagesの反映確認**: デプロイの完了と公開URLを確認する。取得可能ならPages build/deploymentの実行URL・対象コミットを保存する。公開物の一致と起動検証を済ませるまで、人間に「反映済み」と案内しない。
6. **公開版で事前試験**: 対象checkoutから `node mcp/site-smoke-test.mjs --base-url https://mokusatsu.github.io/lyricfx.JIZURA/` を実行する。日本語・英語のHTTP成功、HTML SHA-256一致、初期化・描画を確認する。確認ページとmanifest/fixtureも公開ファイルとローカル期待値を照合する。既存smokeは外部フォント等を止めるため、実際のフォント・素材・その段階の機能は別の公開版確認で補う。
7. **チェックリストを具体化**: [依頼テンプレート](templates/pages-review-request.md)を、その段階の実URL、コミット、サンプル名、操作、期待結果で埋める。個別タスクの「GitHub Pagesでの人間確認」を必須項目として使う。プレースホルダーの残る依頼を送らない。
8. **人間へ依頼**: この会話にURL、対象版、今回の変更、番号付きの確認ポイントを提示し、各項目を`OK / NG / 未確認`で回答するよう依頼する。ブラウザ操作で確認可能にし、開発者コンソールやローカルコマンドの実行を人間の必須手順にしない。外部サービスへのメッセージ送信はこの運用に含まない。
9. **判定と記録**: 人間の回答・対象版・確認環境を個別タスクへ記録する。未回答は承認と扱わない。NGなら当該タスクで修正し、新しいコミットを公開して影響する項目の再確認を依頼する。必須検証と人間の判定が揃うまで完了にしない。

## 公開版の識別と途中段階の扱い

- `work`は更新されるため、URLだけでは版を識別できない。確認ページにはタスクID・build ID・サンプル版を表示し、manifestには日英HTMLとfixtureのハッシュを含める。依頼文には実際にpushしたコミットSHAも記録する。
- 同じコミットにそのコミット自身のSHAを埋め込む設計にしない。公開コミットSHAはGit/Pages実行記録・依頼記録に保持し、公開manifestのbuild IDとファイルハッシュで対応づける。URLへSHAのqueryを付けるだけでは一致証明にならない。
- 人間の確認待ち中は、別段階の版で確認対象を上書きしない。同一段階の修正や他の更新が入った場合は依頼を更新し、旧版への回答と新版への回答を混ぜない。確認待ちを飛ばして依存する次段階へ進めない。
- 全機能が揃う前は通常利用の既定経路を切り替えない。確認専用ページでは、その段階で対応したfixtureに限って新経路を明示的に動かす。未対応レイアウトの自動混入や旧方式への黙示フォールバックは禁止。
- データモデル・resolver等、製品UIへ未接続の段階では、公開確認ページに時刻選択・領域図・結果表等を用意し、実装した関数を実際に呼び出す。後続段階まで人間確認を省略しない。仕様だけの002では「現行実装」と「期待する仕様見本」を明確に分ける。
- 同一`github.io` originでは、パスを変えてもブラウザ保存領域が分かれるわけではない。現行UIも固定の`jizura.project.v1`を使用する。確認サンプルは専用のブラウザプロファイル/新しいプライベートセッションで操作する手順を標準とし、通常の作業データへ自動投入しない。確認ページ側で保存分離を実装する場合はlocalStorageだけでなく関連する素材保存も対象にする。
- GitHub PagesでNode製MCPサーバーやAfter Effectsを実行できるとは扱わない。必要な別環境の自動試験結果を同じ版の証拠として確認ページへ載せ、ブラウザでの操作確認とは区別する。
- 最終017では、以前の段階の判定と自動試験が揃った候補版をPagesへ出し、既定の新方式を含めて人間が確認する。確認前にリリース完了とは扱わず、NG時は原因に応じて修正・再公開する。

## 確認依頼に必ず含める項目

| 項目 | 記載内容 |
|---|---|
| 確認対象 | タスクID、今回の変更、対象コミットSHA、build ID、公開反映を確認した日時（Asia/Tokyo） |
| URL | 日本語版、英語版、対象ケースを開ける確認ページ、サンプル/出力物 |
| 前提 | 推奨ブラウザ・画面サイズ、初期状態、サンプル名、確認専用セッションの開き方、所要時間の目安 |
| 確認ポイント | 安定した項目ID、操作手順、見れば判断できる期待結果、`OK / NG / 未確認`の回答欄 |
| 証拠 | ローカル試験、公開版smoke、公開物ハッシュ、Pages実行記録（取得可能な場合）、画面/動画、既知の制限 |
| 回答方法 | 項目別の判定。NGの場合は項目ID・操作・実際の結果・環境を記載し、可能なら画面を添える |

未使用のUI部品名やサンプル番号を人間に推測させない。個別タスクの予定リストは、実装後に実際のUIと公開ケースに合わせて具体化する。大量の数値検証はエージェントが自動実施し、人間には方向の偏り・可読性・意図した演出・操作感等を見やすく提示する。

## 状態と証拠の置き場所

- ローカル試験成功: `ローカル検証済み`。公開・人間確認は未実施と明記する。
- 公開処理中・公開検証未了・チェックリスト送付後の回答待ち: `実環境検証待ち`。個別記録でどこまで済んだかを示す。
- 公開確認と必須の人間チェックが成功: `実環境検証済み`。必須条件と人間の最終完了判定が揃えば`完了`へ進める。
- 公開失敗や通信制約: 原因とログを記録し、影響しない準備を済ませる。未検証のURLを反映済みとして渡さない。TLS検証を無効化して成功にしない。
- `tasks/reviews/<TASK-ID>-<build-ID>.md`へ実際に渡した依頼文・対象版・回答を保存し、個別タスクからリンクする。`tasks/evidence/<TASK-ID>/`へ公開検証ログ・manifest・画面等を保存する。現時点では未実装のため、架空の公開URLや成功記録でこれらを埋めない。
- 確認ページの最小構成は002、各段階のケース追加・公開・依頼・結果記録は当該段階の変更範囲に含める。最終017へまとめて先送りしない。
