# 各実装段階のGitHub Pages公開と人間確認

2026-10-18の利用者指定により、AVOID-002〜018の各段階は、GitHub Pagesへ出力した版を人間が確認する。担当エージェントが変更前後のキャプチャ画像を準備し、比較HTMLも生成・公開する。公開と反映確認を済ませてから、比較HTML・操作可能なURLと確認ポイントのリストをこの会話で提示する。口頭の説明やローカル試験の成功だけで人間確認を代替しない。

2026-10-18の後続指示で順次実装が許可された。最新の[実装レビュー運用](implementation-review-policy.md)に従い、gpt-6.1-sol mediumが実装し、親がコード・テスト結果をレビューする。人間には動作確認だけを依頼し、親が不要と判断した段階は根拠を記録して次へ進める。以下の人間回答の必須条件は、動作確認が必要と判定した段階に適用する。公開・比較成果物の事前検証は省略しない。

公開依頼と、人間による実装結果の判定は区別する。各段階で公開許可を聞き直す手順は設けず、依頼された実装・公開・事前検証を済ませてから必要な動作確認を依頼する。

- アプリURL: `https://mokusatsu.github.io/lyricfx.JIZURA/`、英語版: `https://mokusatsu.github.io/lyricfx.JIZURA/en/`。既存の `mcp/site-smoke-test.mjs` もこの日本語URLを既定値とする。

- `.github/workflows/verify.yml` は検証用で、Pagesをデプロイする処理はない。Pagesの自動公開と検証CIを別々に確認する。`work`へのpushだけではこのverify workflowの自動実行を意味しない（現行はmain/pull_request/手動起動）。

- 2026-10-20の再確認ではPages APIを読み取れ、既存のlegacy公開元 `work:/` とbuiltを確認した。これは既存公開版の状態であり、準備中のAVOID-006候補の公開完了を意味しない。公開元branch/path・API設定は変更しない。

## AVOID-006の公開容量対策（ローカル準備中）

既存の比較版内部URL・encoded bytes、6言語アプリ、AE/CEP配布物、project、docsを保持するため、全trackedファイルの無選別配備からroot `_config.yml` のJekyll除外指定へ移行する。`.nojekyll` の削除と設定追加は現時点ではローカル準備であり、候補の公開済み・容量検証済みとは扱わない。除外は開発用 `src/dev/app/tasks/tools/work/scratch` 等に限定する。Jekyll既定のdotfile除外で配備されない `mcp/.gitignore`（22 bytes）は開発用ignore設定であり、唯一の非機能ファイル例外として記録する。旧必須素材の欠落を許可する例外ではない。

公開前に、正式な最終候補だけを含むsource snapshotとprojectionを作る。未公開の `review/AVOID-006/local-20261020-01/02/03` とscratchを誤ってstage・配備しない。公式 `ghcr.io/actions/jekyll-build-pages@sha256:6791ebfd912185ed59bfb5fb102664fa872496b79f87ff8b9cfba292a7345041`（Ruby 3.3.4、Jekyll 3.10.0、Liquid 4.0.4、github-pages 232）で実際の出力を作り、`python3 dev/avoidance/pages-output-audit.py --source <snapshot> --output <actual-jekyll-output> --projection <projection.json> --repo . --baseline-ref <着手時HEAD> --candidate-bundle <選択した新review版path> --report <audit.json>` を実行する。projectionは全予定URLと各encoded SHA-256・bytesを持つ `inventory` 配列を含める。監査は全URL集合とsource/output bytesの完全一致、旧公開ファイル保持、manifestの全assetsと共有参照先、総出力1,000,000,000 bytes以下・単blob100 MiB未満を検査する。選択候補以外の未公開review版の混入は失敗させる。manifest内の旧 `../../../index.html`・英語rootのhashは歴史的主張として分け、現在の可変アプリが旧hashと一致するとは扱わない。

試作の実Jekyll出力一致は最終候補の容量合格を代替しない。親による差分・監査結果レビューと最終候補の実Jekyll監査成功後に限ってcommit/pushへ進み、以後も上記のPages反映確認・公開版事前試験を行う。

## 1段階の実行順

1. **変更前の固定と撮影**: 着手時の実装・fixture・撮影条件を固定し、変更前キャプチャを取得する。先行段階の受入済み変更を含む基準にする。[比較画像・HTML契約](visual-review-comparison.md)に従い、新UIが存在しない場合もその事実を残す。
2. **実装とローカル検証**: 個別タスクの条件を満たし、関連する自動試験を実行する。基盤段階も対象とする。
3. **人間が操作できる準備**: その段階の確認用サンプル、操作入口、期待結果を用意する。AVOID-002で公開確認ページ・撮影/比較HTML生成の最小構成を作り、以後は各タスクで必要なケースを追加する。未実装機能を前提に人間へ操作を指示しない。
4. **変更後の撮影と公開物生成**: 日英HTMLを生成し、同条件の変更後キャプチャ、変更前後の比較HTML、fixture、版・画像を識別するmanifestを揃える。各H-IDへ画像ペアを対応づけ、ローカルで比較ページを検証する。アプリ本体と公開用成果物を同じ検証対象として扱う。公開する素材はこの試験用に作成・提供可能なものを使い、実際の演者素材は人間がブラウザ内で読み込む。
5. **コミット・プッシュ**: 当該タスクIDを付けて`work`へコミットし、`origin/work`へ通常pushする。プッシュ先の履歴に別変更があれば内容を確認して取り込み、force pushで消さない。
6. **Pagesの反映確認**: デプロイの完了と公開URLを確認する。取得可能ならPages build/deploymentの実行URL・対象コミットを保存する。公開物の一致と起動検証を済ませるまで、人間に「反映済み」と案内しない。
7. **公開版で事前試験**: 対象checkoutから `node mcp/site-smoke-test.mjs --base-url https://mokusatsu.github.io/lyricfx.JIZURA/` を実行する。日本語・英語のHTTP成功、HTML SHA-256一致、初期化・描画を確認する。比較HTML・全キャプチャ画像・manifest/fixtureも公開ファイルとローカル期待値を照合し、公開ブラウザで画像表示・比較操作・項目リンクを検証する。既存smokeは外部フォント等を止めるため、実際のフォント・素材・その段階の機能は別の公開版確認で補う。
8. **親レビューと確認要否の記録**: コミット前に済ませたコード/テスト結果レビューと公開検証を踏まえ、人間の動作確認が必要かを判断する。不要なら根拠と親の判定を記録し、残る必須条件を満たした上で次へ進む。必要なら[依頼テンプレート](templates/pages-review-request.md)を、その段階の比較HTML実URL、前後の版、撮影条件、各項目への画像リンク、サンプル名、操作、期待結果で埋める。個別タスクの「GitHub Pagesでの人間確認」を必須項目として使う。プレースホルダーの残る依頼を送らない。
9. **人間へ依頼**: この会話に比較HTMLと操作用URL、対象版、今回の変更、番号付きの確認ポイントを提示し、各項目を`OK / NG / 未確認`で回答するよう依頼する。キャプチャの準備は担当エージェントの責務とする。ブラウザ操作で確認可能にし、開発者コンソールやローカルコマンドの実行を人間の必須手順にしない。外部サービスへのメッセージ送信はこの運用に含まない。
10. **判定と記録**: 人間の回答・対象版・確認環境を個別タスクへ記録する。未回答は承認と扱わない。NGなら当該タスクで修正し、新build IDの画像・比較HTMLと新しいコミットを公開して影響する項目の再確認を依頼する。旧画像・依頼・回答は保持する。必須検証と人間の判定が揃うまで完了にしない。

## 公開版の識別と途中段階の扱い

- `work`は更新されるため、URLだけでは版を識別できない。確認ページにはタスクID・build ID・サンプル版を表示し、manifestには日英HTMLとfixture・前後キャプチャ画像のハッシュを含める。比較HTMLは `review/<TASK-ID>/<build-ID>/index.html` に置き、旧版の画像を上書きしない。依頼文には実際にpushしたコミットSHAも記録する。
- 同じコミットにそのコミット自身のSHAを埋め込む設計にしない。公開コミットSHAはGit/Pages実行記録・依頼記録に保持し、公開manifestのbuild IDとファイルハッシュで対応づける。URLへSHAのqueryを付けるだけでは一致証明にならない。
- 人間の確認待ち中は、別段階の版で確認対象を上書きしない。同一段階の修正や他の更新が入った場合は依頼を更新し、旧版への回答と新版への回答を混ぜない。確認待ちを飛ばして依存する次段階へ進めない。
- 全機能が揃う前は通常利用の既定経路を切り替えない。確認専用ページでは、その段階で対応したfixtureに限って新経路を明示的に動かす。未対応レイアウトの自動混入や旧方式への黙示フォールバックは禁止。
- データモデル・resolver等、製品UIへ未接続の段階では、公開確認ページに時刻選択・領域図・結果表等を用意し、実装した関数を実際に呼び出す。後続段階まで人間確認を省略しない。仕様だけの002では「現行実装」と「期待する仕様見本」を明確に分ける。
- 同一`github.io` originでは、パスを変えてもブラウザ保存領域が分かれるわけではない。現行UIも固定の`jizura.project.v1`を使用する。確認サンプルは専用のブラウザプロファイル/新しいプライベートセッションで操作する手順を標準とし、通常の作業データへ自動投入しない。確認ページ側で保存分離を実装する場合はlocalStorageだけでなく関連する素材保存も対象にする。
- GitHub PagesでNode製MCPサーバーやAfter Effectsを実行できるとは扱わない。必要な別環境の自動試験結果を同じ版の証拠として確認ページへ載せ、ブラウザでの操作確認とは区別する。
- 最終017では、以前の段階の判定と自動試験が揃った候補版をPagesへ出し、既定の新方式を含めて親が確認し、必要な人間の動作確認を依頼する。確認前にリリース完了とは扱わず、NG時は原因に応じて修正・再公開する。

## 確認依頼に必ず含める項目

| 項目 | 記載内容 |
|---|---|
| 確認対象 | タスクID、今回の変更、対象コミットSHA、build ID、公開反映を確認した日時（Asia/Tokyo） |
| URL | 変更前後の比較HTML、項目別アンカー、日本語版、英語版、操作用確認ページ、サンプル/出力物 |
| 比較条件 | 変更前/変更後の版、fixture、seed、寸法・DPR、時刻、フォント/ブラウザ、取得方法。条件差と旧版にない機能を明示 |
| 前提 | 推奨ブラウザ・画面サイズ、初期状態、サンプル名、確認専用セッションの開き方、所要時間の目安 |
| 確認ポイント | 安定した項目ID、操作手順、見れば判断できる期待結果、`OK / NG / 未確認`の回答欄 |
| 証拠 | ローカル試験、公開版smoke、比較HTML・全画像等の公開物ハッシュ、Pages実行記録（取得可能な場合）、前後キャプチャ/必要な連続コマ、既知の制限 |
| 回答方法 | 項目別の判定。NGの場合は項目ID・操作・実際の結果・環境を記載し、可能なら画面を添える |

未使用のUI部品名やサンプル番号を人間に推測させない。個別タスクの予定リストは、実装後に実際のUIと公開ケースに合わせて具体化する。大量の数値検証はエージェントが自動実施し、人間には方向の偏り・可読性・意図した演出・操作感等を見やすく提示する。

## 状態と証拠の置き場所

- ローカル試験成功: `ローカル検証済み`。公開・人間確認は未実施と明記する。
- 公開処理中・公開検証未了・チェックリスト送付後の回答待ち: `実環境検証待ち`。個別記録でどこまで済んだかを示す。
- 公開確認と必要な人間の動作チェックが成功、または動作確認不要の根拠が記録済み: `実環境検証済み`。必須条件と親の最終判定が揃えば`完了`へ進める。人間が未確認の事実と不要判定を区別する。
- 公開失敗や通信制約: 原因とログを記録し、影響しない準備を済ませる。未検証のURLを反映済みとして渡さない。TLS検証を無効化して成功にしない。
- `tasks/reviews/<TASK-ID>-<build-ID>.md`へ実際に渡した依頼文・対象版・比較URL・回答を保存し、個別タスクからリンクする。`tasks/evidence/<TASK-ID>/`へ公開検証ログと成果物のパス/ハッシュを保存する。公開する画像・比較HTML・manifestは上記の版付きreview配下を正本とし、証拠へ重複コピーせず追跡可能にする。現時点では未実装のため、架空の公開URLや成功記録でこれらを埋めない。
- 確認ページ・キャプチャ/比較HTML生成の最小構成は002、各段階のケース追加・撮影・生成・公開・依頼・結果記録は当該段階の変更範囲に含める。最終017へまとめて先送りしない。
