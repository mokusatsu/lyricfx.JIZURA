# 変更前後キャプチャと比較HTMLの受入契約

2026-10-18の利用者指定により、各実装段階で担当エージェントが確認対象のキャプチャ画像を準備し、変更前後を視覚確認できるHTMLを生成してGitHub Pagesへ公開する。[Pages人間確認運用](pages-human-review.md)の必須成果物とする。これは後続実装の計画であり、この文書の追加時点で画像・比較HTMLの生成や公開を済ませたという意味ではない。

AVOID-002で共通の撮影・HTML生成・検証手順を用意し、AVOID-003〜018はそれを使って各段階の画像と比較ページを追加する。個別タスクのH01〜H03（全51項目）を一つも省略せず、各項目に比較ケースを対応づける。画像の準備を人間へ委ねず、担当エージェントが公開物を確認した後にチェックリストを渡す。

## 変更前と変更後の定義

- **変更前**: 当該段階の着手時に固定した、先行段階の受入結果を含むブランチの実装。コミットSHAと生成物を保持する。単に依存タスクの古いコミットを選び、間に入った段階の変更を落とさない。002では現行実装を使う。
- **変更後**: 当該段階の実装・ローカル検証を済ませ、公開する候補の実装。同じ生成物を撮影・公開検証・人間確認に使う。修正があれば新しいbuild IDで撮り直す。
- 機能導入前のアプリ基準 `b7c23bff8a04019b9b90357b433927995834ae62` も保持する。最終017では「その段階の前後」に加え、代表ケースについて「機能導入前→最終候補」の累積比較を別欄で示す。途中段階の前後比較と混同しない。
- 変更前は隔離したcheckout/worktree等で再現し、作業中のブランチや利用者データを巻き戻さない。旧版が新schemaを読めない場合は、共通部分の入力と変換規則、比較できない新項目を明示する。新データを旧版に読ませて黙って無視された結果を同等入力と呼ばない。
- 新UI・resolver等が旧版にない場合は、旧版の実画面または旧版を実行した確認用ページの「機能なし/未接続」の観測結果を示し、同じ操作ができない点を明記する。新機能が存在したような変更前画像を作らない。002の仕様見本は「未実装の仕様見本」と表示し、現行/変更後の実測画像とは別枠にする。
- 002の変更後は、実際に追加した確認ページ・契約表示と現行描画のキャプチャであり、新しい回避軌道の完成画像ではない。見た目が不変であるべき対照ケースは同じ画像になることも正しい結果として扱う。
- 既存の解析画像 `existing-ring-avoid.png` は外部フォントを読み込まない条件の記録。同じ条件を再現せず、新しい比較の変更前として流用しない。

## 撮影条件と画像の種類

各比較ケースで以下を固定・記録する。意図した差分以外に条件差がある場合は理由を表示し、同条件の比較とは扱わない。

| 分類 | 固定する条件 |
|---|---|
| 入力 | fixture ID・版・ハッシュ、歌詞、seed、レイアウト/効果、回避設定、手動/ロック、メディア・動画の対象フレーム、初期保存状態 |
| 寸法 | stage寸法・アスペクト、出力寸法、ブラウザviewport、DPR、zoom、UI言語、選択/スクロール状態 |
| 描画 | ブラウザ/OS/フォントの版と読み込み結果、fast/full、camera・FX、背景/前景、ガイドON/OFF |
| 時間 | プロジェクト実時刻、fps・フレーム番号、量子化時刻、cut/group、再生/seekの到達経路。残像を使う場合の履歴とlag |
| 取得 | 撮影方法・コマンド・環境、取得日時、ローカル候補/公開Pages/別実行環境の区別、画像の画素寸法・SHA-256 |

- フォント・素材の読み込み、動画のseek完了、対象フレームの描画完了を待って撮影する。固定秒数のsleepだけを撮影条件にしない。再生中の任意の瞬間を撮らず、同じ時刻へ決定的に到達させる。読み込み失敗は記録し、通常ケースを黙って代替フォントで合格させない。
- 通常は読み込み完了後を比較する。004等のフォント遅延/失敗試験では、制御した未読込・読込済み状態を別ケースとして記録し、条件差そのものを確認対象とする。
- 軌道はenter/hold/exitを、区間・cut切替は `t−ε / t / t+ε` を同じ規則で採取する。εと実際の描画時刻を記録し、時刻量子化で3枚とも同じ状態になった場合は境界検証成功としない。動きは連続コマを並べ、必要に応じて短い録画も併記する。
- UI変更はトラック全体・操作部・編集画面を含むブラウザキャプチャ、描画変更は同じ出力寸法の描画面PNGを用意する。選択枠/ガイドと描画の関係が対象なら両方を載せる。UI全体を切り抜いて位置関係を隠さない。
- 元画像は可逆PNGで保存し、片側だけ縮小・トリミング・着色して差を隠さない。拡大切抜きや注釈は比較ページの補助表示とし、未加工の全体画像も開けるようにする。スマートフォン等の別環境比較は条件を分ける。
- 018/016の透過確認ではalphaを保持したPNGと、同じ背景へ合成した結果を用意する。比較HTMLでは同じ市松・明/暗背景へ切り替えられるようにし、白背景への平坦化で透過を示したことにしない。円内/外周/円外、主歌詞・動画の非干渉を確認できる倍率にする。
- 016の出力比較は実際のPNGとMP4から同時刻で取り出したフレームを区別して掲載する。プレビューの画像を出力ファイルの証拠として代用しない。

画像は視覚判断の証拠であり、連続軌道の全時刻安全性、保存データの完全性、Undo回数、性能を証明するものではない。独立した自動検証と実操作を併用する。数値や内部状態の確認項目には、実装した関数から得た結果表のキャプチャと元データ/ログを添える。期待値だけを描いた表を実測値と表示しない。

## 比較HTMLと配置

後続実装時の配置を次に揃える。`<…>`は予定パスの変数であり、現時点で存在するURLではない。

```text
review/<TASK-ID>/<build-ID>/
  index.html
  manifest.json
  images/<case-ID>-<frame-ID>-before.png
  images/<case-ID>-<frame-ID>-after.png
  fixtures/...
```

公開URLは `https://mokusatsu.github.io/lyricfx.JIZURA/review/<TASK-ID>/<build-ID>/index.html`。補助CSS/JS等も同じ版の配下へ保存し、画像・fixtureへの参照を相対パスにしてリポジトリのサブパス配信に対応する。同じタスクの再修正でも旧build IDのファイルを上書きしない。公開済み比較ページからは、その版の画像とfixtureを参照する。

比較HTMLの必須要件:

1. 上部にタスクID、build ID、変更内容、変更前/変更後の版識別子、撮影条件、未実装/未確認の範囲を表示する。公開コミットSHAは後述の外部記録と対応づける。
2. 項目IDごとの見出しと固定アンカー（例 `#AVOID-014-H01`）を設け、チェックリストの各項目から直接開けるようにする。1項目に複数ケース/時刻が必要なら全て並べる。目次には項目数・ケース数を表示し、欠けた画像を空欄のまま合格対象にしない。
3. 「変更前」「変更後」を同じ縮尺で左右に並べ、各画像にケース名・時刻・版を表示する。狭い画面では前→後の順で縦に並べ、ラベルを保持する。原寸表示と同期した拡大表示を用意し、文字やグラデーションを読めるようにする。
4. 切替/重ね合わせ表示も用意し、キーボードで操作できるようにする。差分画像を補助表示する場合は算出条件と凡例を付け、画像差分の大小だけで合否を決めない。
5. 各ケースに「見る箇所」「意図した変化」「維持すべきもの」を短く書き、操作用Pagesページ、同じfixture、関連する自動試験証拠をリンクする。静止画の比較と操作確認を一緒に依頼する。
6. 動画・スクロール・アニメーションの自動再生を必須にせず、画像だけでも前後の関係が分かるようにする。モバイルで横に切れて画像や説明を読めない状態を残さない。

### manifestと版の追跡

002で具体的なschemaと生成コマンドを確定し、最低限以下を持たせる。

- task ID、build ID、比較ページの版、対象H-IDの一覧。
- 各case IDとH-IDの対応、上記の撮影条件、fixture/素材のハッシュ、適用した入力変換と既知の比較不能箇所。
- 前後それぞれの実装識別子（確定済みコミットSHA、候補が未コミットなら基準SHAとソース内容ハッシュ）、実際に撮影したHTML/JS・fixtureのハッシュ。
- 前後それぞれの画像パス、画素寸法、SHA-256、フレーム時刻、取得方法、撮影環境、取得日時。原寸画像と補助画像を区別する。
- 公開用日英HTML・確認用fixture・補助ファイルのハッシュ。manifest自身のハッシュは公開検証ログに記録し、自己参照で計算しない。

同じコミットに自身のSHAを埋め込まない。公開コミットSHA、デプロイ実行URL（取得できる場合）、比較HTML/manifestのハッシュは `tasks/reviews/<TASK-ID>-<build-ID>.md` と公開検証記録で対応づける。ローカル候補を撮影してから公開した場合は「ローカル候補を撮影、公開物との一致を確認」と記載し、「Pages上で撮影」と偽らない。画像ファイルの一致確認に加え、その画像を生成したアプリ/fixtureと公開対象版が一致することも検証する。

## 生成・検証・依頼の完了条件

1. 着手時の変更前実装と比較入力を固定し、変更前を撮影する。変更後と同じ条件で再現できない場合は、理由・比較可能な範囲を記録する。基準画像を後から都合よく置換しない。
2. 実装と自動試験後、変更後を撮影し、manifestからHTMLを生成する。H01〜H03全項目の実画像ペア、必要な複数時刻、ライブ操作入口が揃うことを機械確認する。新機能不在は上記の明示方法を使う。
3. ローカルで画像の読込・サイズ・前後の取り違え・項目へのリンクを確認し、デスクトップ/狭い画面でHTMLを実際に開く。画像の未取得、空の画像、再描画未了、読み込み失敗を成功にしない。
4. `work`へ画像・比較HTML・manifest・fixtureをアプリの対象版とともにコミット/pushする。Pages反映後にHTML、全画像、manifest等のHTTP成功とハッシュ一致、ブラウザでの画像表示（naturalWidth等）と比較操作、関連アプリの起動を検証する。トップページのHTTP 200だけで済ませない。
5. [依頼テンプレート](templates/pages-review-request.md)へ比較HTML実URL、前後の版、各H-IDへのリンク、撮影条件、操作・期待結果を記入して人間へ渡す。人間は各項目を `OK / NG / 未確認` で回答する。画像の準備やローカル生成作業を依頼しない。
6. NG修正は新しいbuild IDで変更後を再取得・再公開し、影響する項目を再確認する。着手時の変更前と旧版の依頼・画像・回答を保持する。基準そのものを変更する必要があれば理由を記録し、前後の条件を再照合する。

撮影不能・公開画像欠損・条件不一致・人間未確認が残ればその項目は未達/未確認。比較HTMLを生成しただけではタスクを完了にしない。公開準備と人間判定の状態・引き継ぎは[共通運用](pages-human-review.md)に従う。
