## Camera qualification before any rest-source gate

A constant native-layout rest displacement is not automatically a constant SCREEN
translation under stock push. With output p(t)=M(t)x(t)+b(t), changing x to x+dg
adds M(t)dg and adds M'(t)dg to output velocity. Uniform push generally has
M'(t)!=0. Therefore native rest constants preserve layout-space motion but cannot
be claimed to preserve exact screen displacement/velocity for nonzero dg under
that camera. Do not silently label both invariants proved.

If exact screen trajectory differences are required, a different separately
reviewed family can apply CONSTANT STAGE-space dg/da/de to already camera-mapped
original points. Then each source point keeps its original output velocity and
shape/font/camera scaling. For strings, apply constant per-vertex(1-f)dg+f*de;
for glyph copies/knot/highlight/anchor, constant per-owner stage translations.
An implementation might inverse-map these stage deltas through the original live
camera root for source arguments/contexts, but its layout-space correction would
vary with camera and must NOT be described as constant native rest coordinates.
This would need a fresh balloons-only source/pixel/kinematic gate, zero-delta
identity, all-owner/copy attachment proof, no generic bridge, and a new continuous
support model. It is a read-only alternative, not an authorized recipe.
