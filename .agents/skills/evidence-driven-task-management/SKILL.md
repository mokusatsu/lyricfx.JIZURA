# Evidence-Driven Task Management

開発タスクを会話ではなくリポジトリ内の記録で管理し、第三者が追跡できる証拠で完了を判定する。

## 基本原則

- 既存の規約がなければ `tasks/task-list.md` をタスク一覧の正本にし、個別タスクの詳細を `tasks/<TASK_ID>.md` に分けて管理する。
- 原則として進行中のタスクを1件に限定する。独立したブランチまたはworktreeに分離されている場合だけ複数実装を許容する。
- タスクIDを再利用しない。取りやめた行も削除せず、`中止` または `対象外` と理由を残す。
- 実装、テスト、文書更新、差分確認を1タスクの作業単位にする。
- AIの自己申告や進捗率ではなく、差分、テスト結果、ログ、実環境確認などの証拠で状態を更新する。
- `実装済み`、`ローカル検証済み`、`実環境検証済み`、`完了` を区別する。
- 優先順位、事業判断、リスク受容、最終完了判定を人間の判断として扱う。
- リポジトリ固有の `AGENTS.md`、開発規約、既存のタスク形式がある場合はそちらを優先する。

## タスク管理を初期化する

1. `AGENTS.md`、関連仕様、既存のタスク管理ファイル、ビルド・テスト手順、Git状態を確認する。
2. タスク管理の導入を依頼され、正本が存在しない場合だけ `assets/task-list-template.md` を `tasks/task-list.md` へコピーして調整する。`tasks/` がなければ作成し、既存ファイルを上書きしない。
3. タスクIDの接頭辞、状態の定義、必須証拠、役割分担をプロジェクトに合わせて明記する。
4. 一覧には各タスクのID、名前、状態、依存関係、個別詳細へのリンクを記録し、目的、範囲、完了条件、証拠はタスクID別ファイルへ記録する。優先度と備考も必要なら一覧または個別ファイルへ追加する。
5. 完了条件を第三者がYes/Noで判定できる文にする。「適切に動作する」など曖昧な表現を具体化する。

既存の正本が別パスにある場合は、ユーザーから移行の指定がない限り移動せず、そのファイルを使う。移行を指定された場合は `tasks/` を作成し、既存の詳細を失わないよう `tasks/<TASK_ID>.md` へ分離してから `tasks/task-list.md` を作成し、現行参照も更新する。複数の候補がある場合は、どれを正本にするかユーザーへ確認する。

## 一覧と個別タスク記録を分離する

- `tasks/task-list.md` は一覧専用とする。1タスク1行を基本に、ID、題名、状態、必要なら優先度・依存関係、`<TASK_ID>.md` への相対リンクを置く。目的、完了条件、長い検証ログ、引き継ぎ内容を一覧へ重複転記しない。
- `tasks/<TASK_ID>.md` はタスクの詳細記録とする。目的、変更範囲、禁止事項、完了条件、テスト方法、停止条件、開始時確認、実施証拠、残事項、引き継ぎを記録する。ファイル名は一覧のタスクIDと完全に一致させる。
- 新しいタスクを登録するときは、未使用のIDで個別ファイルを作成し、一覧にリンク付きの行を追加する。個別ファイルだけ、または一覧だけを更新した状態で作業を開始しない。
- 状態や題名を変更したときは一覧と個別ファイルを同じ変更で同期する。詳細な証拠や履歴は個別ファイルへ追記し、一覧は現在の状態をすばやく把握できる大きさに保つ。
- 完了・中止したタスクも一覧と個別ファイルから削除せず、IDを再利用しない。古い記録を別場所へ移す必要がある場合も、一覧から追跡できるリンクを残す。

## 1タスクを定義する

必要に応じて `assets/task-brief-template.md` を `tasks/<TASK_ID>.md` の雛形としてコピーし、次を明文化する。

1. 目的: 何を変えるかだけでなく、なぜ変えるかを書く。
2. 変更範囲: 調査・変更してよい機能、ファイル、データを限定する。
3. 禁止事項: 互換性破壊、無関係な修正、根拠のない仕様補完などを列挙する。
4. 完了条件: 観測可能で二値判定できる条件にする。
5. テスト方法: unit、integration、regression、実環境確認のうち必要なものと未実施の扱いを決める。
6. 停止条件: 人間の判断が必要になる境界を決める。

## タスクを開始する

1. ユーザーが指定したタスクIDを優先する。指定がない場合は依存関係、優先度、着手可能性から候補を提示し、事業優先度を勝手に確定しない。
2. すでに進行中のタスクがある場合は、新しいタスクを開始せず、継続、保留、または終了の判断を求める。
3. 依存タスクの完了と、対象タスクの個別ファイルに6項目が揃っていることを確認する。
4. 開始時のブランチ、HEAD、`git status` を個別タスクファイルへ記録する。
5. 未確認の既存変更が対象ファイルと重なる場合は変更前に停止する。無関係な既存変更は記録し、保持して作業対象から除外する。
6. 個別タスクファイルの状態を `調査中` または既存規約の対応状態へ更新し、一覧の状態とリンクを同期してから対象タスクだけを進める。

## タスクを実行する

- ユーザーが管理・計画・報告だけを求めている場合は、実装まで広げない。
- 変更範囲が広い場合は、参照箇所、変更予定ファイル、互換性への影響、テスト、未決事項、ロールバック方法を先に計画する。
- 対象範囲だけを変更し、無関係なリファクタリングや警告修正を混ぜない。
- 修正前の失敗を再現できる場合は記録し、修正後に同じ条件で成功することを確認する。
- テストの期待値を実装へ合わせる場合は、仕様上の根拠を示す。テストを通すためだけに期待値を変更しない。
- コード、テスト、関連文書、`tasks/task-list.md`、対象の個別タスクファイルを同じタスク内で同期する。
- Gitのコミット、push、PR作成は、ユーザーが依頼または明示的に許可した場合だけ行う。その場合はタスクIDをブランチ名、コミット、PRへ含める。

作業中に問題を発見したら、次のように分類する。

1. 現在の完了条件に必須: 現タスクへ含め、理由を記録する。
2. 関連するが別の完了条件: 新しい未着手タスクとして登録し、現タスクを継続する。
3. 無関係な既存問題: 新しい未着手タスクまたは既知事項として記録し、現タスクを継続する。

新規タスクには未使用のIDを発行し、元タスクとの関連や依存関係を残す。

## 状態と進捗を更新する

プロジェクト固有の定義がなければ、次を使う。

| 状態 | 判定基準 |
|---|---|
| 未着手 | 調査も実装も開始していない |
| 調査中 | 仕様または既存コードを確認している |
| 実装中 | 対象の変更を行っている |
| ローカル検証済み | 必要なローカル自動テストや確認が成功した |
| 実環境検証待ち | ローカル検証は済んだが、必要な実環境確認が残る |
| 完了 | すべての完了条件と必須検証を証拠付きで満たした |
| 保留 | 外部回答、権限、仕様決定などを待っている |
| 中止 / 対象外 | 実行しない判断と理由が記録されている |

進捗率は補助情報として扱い、変更ファイル数から機械的に推定しない。必須検証が残る間は100%にしない。

## 完了を判定する

1. 完了条件ごとに `達成`、`未達`、`未確認` を付け、対応する証拠を列挙する。
2. 変更ファイル、主要差分、実行コマンド、テスト件数と結果、再現結果、実環境確認、データ識別子、未実施項目を収集する。
3. 開始時と終了時のブランチ、HEAD、`git status`、コミットまたはPRがあればその識別子を記録する。
4. すべての完了条件と必須検証を満たした場合だけ `完了` にする。実環境確認が必要で未実施なら `実環境検証待ち` にする。
5. 個別タスクファイルの状態、証拠、残事項を更新し、`tasks/task-list.md` の一覧状態とリンクを同期してから完了報告する。
6. 必要に応じて `assets/completion-report-template.md` を使い、成功だけでなく未確認事項も正確に報告する。

## 停止する

次を検出したら、新たな変更を止めてユーザーの判断を求める。

- 仕様書同士、または仕様と完了条件が矛盾する。
- データ削除、不可逆な変換、破壊的マイグレーションが必要になる。
- 公開APIの互換性、認証、決済、個人情報、契約、セキュリティへ予期しない影響がある。
- 本番設定、追加権限、認証情報が必要になる。
- 変更範囲を超える大規模設計変更が必要になる。
- 対象箇所がユーザーの既存変更と競合する。
- 完了条件を根拠なく補完しなければ進められない。

停止報告には、停止理由、確認済みの事実、ファイル変更の有無、現在のGit状態、判断が必要な点、選択肢と影響を含める。

## 複数担当で引き継ぐ

- ユーザーが複数エージェントや担当者の利用を求めた場合だけ分担する。
- 同じファイルやデータへ書き込む実装を並列化しない。独立した調査やテストだけを同じ作業ツリーで並列化する。
- 複数実装を並列化する場合は、ブランチまたはworktreeを分離し、1タスク1責任者を明確にする。
- 引き継ぎ情報を個別タスクファイルへ記録し、タスク一覧から追跡できるようにする。内容はタスクID、目的、変更範囲、禁止事項、完了条件、停止条件、実差分、テスト結果、未確認事項、判断点へ絞る。
